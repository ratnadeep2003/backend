There are a lot of ways for client and server to communicate, HTTP is the most common of them.

HTTP: a medium through which browsers communicate with servers to send or recieve data. It is an application layer protocol.

There are 2 core concepts for http: 
    1. Stateless: having no memory of past interaction. After the first request from client is served, http server forgets about it and what is sent and looks for serving other request. 
    Because http is stateless, state management techniques such as cookies or session management are implemented so that theres no need to send auth tokens with each request to the server.

    2. Client-server model: communication is always initiated by the client and never by the server, server only responds to incoming requests. 

    In this client-server model, the connection is made of TCP. The major difference between TCP and UDP is:   
        • TCP is a connection-oriented, reliable protocol that guarantees data delivery, while UDP is a connectionless, faster protocol that sends data without guarantee.

        • TCP uses 3 way handshake to connect, UDP sends data immediately without setting up connection

                3 way handshake: 
                    Step 1: SYNC-> client says to server that it wants to connect
                    Step 2: SYNC-ACK-> server says 'i hear you lets connect'
                    Step 3: ACK-> client says ok lets connect

Basic working of request and response: client sends a request, browser responds to it.

    Elements    Example

    Body	    {name: "John Doe", profile:'picture.jpg'}   -> to pass the main data

Response view: 
    Elements    Example
    Header	    Content-Type: text/html; charset=utf-8
    ------a blank line to signify all headers are over------
    Body	    {message: 'Welcome!!!', pic: 'smiley.png'}

Headers: are basically key value pairs used to provide additional info. 
Different types of headers: 
    1. Request-headers: provides info about the request itself
        • User agent :to signify who is sending the request, if it browser or mobile app or postman 
        • Auth headers: sends bearer tokens to identify right user.
        • Accept headers: to identify what type of content receiver is expecting like json or text

    2. General headers: used in both request and response.
    example: date, cache control, connection etc 

    3. Security headers: enhance security of the request and response.
        • Strict transport security (htts): ensires client only communicates with server in https
        • Content security policy (CSP): restricts the resources from which js can be loaded 
        • x-frame-options: Controls whether your website can be embedded inside an <iframe>, <object>, or <embed> tag on another website.
        • x-content-type-options: Forces the browser to strictly follow the declared file type and prevents it from guessing (or "sniffing").
        example: By setting X-Content-Type-Options: nosniff, you tell the browser: "Trust the Content-Type header explicitly. If I say it's an image, do not try to execute it as code."
        • set-cookies: A response header sent by the server to tell the browser: "Hey, save this piece of data and send it back to me on every future request." This is how authentication sessions work.

HTTP methods: GET/ POST/ PUT/ PATCH/ DELETE/ OPTIONS-> provide the intent of the url's interaction with the server
    1. GET: retrives data from server
    2. POST: submits an entity to the server
    3. PUT: replaces all current representation of target resource with request content
    4. PATCH: used to apply partial modifications to a resource
    5. DELETE: used to remove a resource identified by a given url
    6. OPTIONS: fetch the capabilities of a server for a cross origin request

In a cross origin request, there are 2 types of flows:
    1. Simple request flow:
        client                                          server
        example.com                                     api.example.com (this is the host)
        
        GET /api/products/123 HTTP/1.1
        Host: api.anotherdomain.com
        Origin: example.com
        Accept: application/json
        (if the server accepts this, the response is:)---> HTTP/1.1 200 ok
                                                            Content type: application/json
                                                            Access control allow origin: example.com

                                                            {
                                                                "product" : {
                                                                    "id": 123,
                                                                    "name": "example product,
                                                                    "price": 43
                                                                }
                                                            }
                                                     
    2. Preflight request flow: there are conditions where a browser decides a request flow is eithe simple or preflight. It is made with the OPTIONS method.
            • it has to be a cors request, meaning the server and client domain have to be different (compulsory), or any of the following one must be true
            • the method should not be GET/ POST/ or HEAD/
                        OR
            • the request includes non simple headers, anything apart from general or request headers 
                        OR  
            • the request has a content-type other than application/x-www-form-urlencoded, multipart/form-data or text/plain and sends json data. 
    example: 
    broswer request-> OPTIONS api/resource HTTP/1.1
                      Post: api/anotherdomai.com
                      Origim: example.com
                      Access-control-request-method: PUT
                      Access-control-request-header: Authorization
    
    server response-> HTTP/1.1 no content
                      Access-control-allow-origin: example.com
                      Access-control-allow-method: PUT, DELETE
                      Access-control-allow-header: Authorization
                      Access-control-max-age: 86400

TLDR: 
    1. for the request to be a simple request, it must be a cors request meaning host and origin must be on different ports, and if the server returns a reposne with access-control-allow-origin heder then the client receives the response, if access-control-allow-origin heder is blocked, the client receives no response. 

    2. for pre flight request, it must be first OPTIONS, followed by a cors or GET, POST, DELETE. Preflight dont have request or response bodies. If the preflight request is successful, it sends a status code of 204 and then the original request of PUT or DELETE is executed.

HTTP Caching: is a technique used to store copy-server responses for reuse, reducing the need to send multiple requests to the server. how is this implemented ?

Content negotiation: explains how client and server exchage information. Client describes its desired format as json or xml, server tries to respond with the same format and if not it also has a fall back format. This is done mostly through Content type: application/json. 

Handeling large request-reponse: 
    1. Multipart request: defines how clients can send large requests to server. Here Content-type becomes multipart/form-data. 
    2. Streaming response: defines how servers can send large responses to the client. Streams large data from server to client in chunks. Content-type here is text/event-stream. Another header of Connection: keepa-live is made so that the connection bteween client and server stays up until all the data is sent from server to client.

SSL and TLS: SSL (Secure Sockets Layer) and TLS (Transport Layer Security) are security protocols that encrypt data sent between a web browser and a server to keep information private and safe. 

    SSL: It builds a safe, encrypted link between a website and a user.
    TLS: Modern upgraded version of SSL, It secures internet traffic with stronger encryption algorithms and faster connection handshakes.

HTTPS: its just http with security fatures provided with tls. When you visit a website using https, tls encrypts the communication between your browser and server.

CORS applies whenever there is a difference in Origin, which is defined as the combination of Scheme (http/https) + Host (domain) + Port. Even if the domain is the same, changing the port (e.g., frontend on http://localhost:3000 talking to backend on http://localhost:5000) triggers CORS!


Method Safety & Idempotency (Crucial Interview & Design Concept): HTTP methods are grouped by their behavioral safety guarantees

    1. Safe: Does not alter the state on the server (read-only).
    Methods: GET, HEAD, OPTIONS
    Why it matters: Search engines can safely pre-fetch links without accidentally deleting or buying things.
    
    2. Idempotent: Making the same request multiple times yields the exact same server state as making it once.
    Methods: PUT, DELETE, GET
    Why it matters: If a network glitch causes a client to retry a DELETE request 3 times, it doesn't change the final result—the resource is still deleted.

    3. Non-Idempotent: Making the same request multiple times can create multiple distinct states or resources.
    Method: POST
    Why it matters: If a POST /api/pay request retries due to a timeout, you might accidentally charge the user's credit card twice unless the operation is handled carefully.
